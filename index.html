Project overview

Schools send the same kinds of announcements again and again. This project explores how to automate that work without losing control over what is sent and to whom.

Purpose

Help schools manage notices and send important announcements to parents more efficiently, with less repeated manual effort.

Approach

Google Sheets holds campaigns, parent contacts and logs. n8n coordinates the workflow. TextBee connects to an Android SMS gateway for delivery.

Where it stands

A working prototype. Test SMS messages have been received, but it has not been deployed to production.

Problem statement

Notices reach parents slowly when staff have to send each one by hand.

Sending school notices by hand is slow, repetitive and hard to trace.The same announcement has to reach many parents. Doing this manually means repeated effort, a real chance of wrong or duplicate messages, and no clear record of what was sent. The goal: let an approved notice in a sheet go out as SMS in a controlled, logged way.

Repetitive work

The same notice has to be copied and sent to many recipients.

Risk of mistakes

A wrong recipient, a missed contact or a duplicate message is easy to make by hand.

Little traceability

Without a record, it is hard to know what was attempted or what went wrong.

Proposed solution

One workflow reads an approved campaign, checks it, sends messages one recipient at a time, and records every result. The badges show where each part stands today.

Start and safety gate

The workflow runs on a one-minute schedule or a manual test trigger.

  • Workflow config
  • Read campaign
  • Campaign gate
  • Gate open?
  • Lock campaign
  • Verify lock

If the gate is closed, there is nothing to do. If the campaign needs attention, it is flagged and the run stops with an error.

Plan the recipients

Contacts are read and sorted into send, skip or nothing to send.

  • Read contacts
  • Plan recipients
  • Dry run?
  • Route plan items

In a dry run, the workflow writes a report and a log entry and sends nothing. Skipped rows are marked in the sheet.

Send loop, one recipient per request

Each contact is re-checked right before sending.

  • Re-read contact row
  • Guard row
  • Row still eligible?
  • Mark processing
  • Send SMS via TextBee
  • Classify response
  • Record result
  • Fatal error?
  • Pause between sends

A fatal error stops the send. Otherwise the loop pauses, then moves to the next recipient.

How the system works

The steps below follow one run from trigger to log entry.

  1. The workflow starts

    A schedule checks every minute in the Asia/Kathmandu time zone. A manual trigger is available for testing. Safe defaults apply: dry run is on and each run is limited to one recipient.

  2. The campaign is checked

    The campaign must be marked approved, have an approver, a valid send date and time, a message, and a valid live-mode setting. It must also fall inside its expiry and grace window.

  3. The campaign is locked

    The workflow writes a processing status before the HTTP request and verifies it, so another run does not pick up the same campaign.

  4. Recipients are planned

    Contacts are read and each one is marked to send or skip. A dry run stops here with a report.

  5. Messages are sent one at a time

    Each contact row is re-read and validated, then marked as processing before the request goes to TextBee. The response is recorded as accepted, failed or unknown. There are no automatic retries.

  6. The run is logged

    The workflow summarizes the run, updates the campaign’s status note and adds an entry to the run log.

Challenges and lessons learned

Testing has already shown where an SMS workflow can go wrong.

An uncertain result

An earlier execution timed out and it was unclear whether the message was delivered. The workflow now marks such results as unknown instead of guessing.

Accepted is not delivered

TextBee accepting a request means it was queued. It does not prove the parent received the SMS, so the workflow records the two differently.

Retries can cause duplicates

Blindly retrying an uncertain send could message a parent twice. The workflow does not retry automatically, and stuck or unknown items need manual review.

Sheets is not a database

Google Sheets cannot guarantee atomic locks or unique keys. Running one workflow at a time helps, and a database such as PostgreSQL would be stronger.

Safe defaults help

Starting in dry run with a one-recipient limit makes it cheap to test changes without messaging real parents.

Logs make problems visible

Recording each attempt and outcome makes failures easier to investigate.
